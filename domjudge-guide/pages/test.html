스트레스 테스트 시나리오

🔥 대회 전, 반드시 리허설이 필요한 이유

대회 당일 서버가 다운되면 복구가 사실상 불가능합니다. 이 스트레스 테스트는 단순히 서버의 작동 여부를 확인하는 것이 아니라, 실제 챌린지 환경을 모의하여 인프라의 한계를 미리 파악하고 대비하는 가장 중요한 과정입니다.

네트워크 망 안정성

수십 명의 학생이 동시에 접속할 때 발생하는 네트워크 대역폭 병목을 사전에 점검합니다.

로그인 및 세션 관리

동시 다발적인 로그인 요청 시 DB와 세션 관리자가 정상적으로 응답하는지 확인합니다.

인프라 최적화 근거

테스트 결과에 따라 캐시, 채점기(Judgehost) 확장, 하드웨어 증설 여부를 결정합니다.

🚀 테스트 전 준비사항

서버 구축 완료 후, 실제 대회와 유사한 부하를 주어 시스템의 안정성을 검증합니다. 최소 5명 이상의 교사가 동시에 참여하는 것을 권장합니다.

  • 계정 준비: 테스트용 팀 계정(Team) 5~10개와 관리자(Jury) 계정 1개
  • 관찰 도구: Jury Interface의 Judging Lag 그래프 및 서버의 htop 모니터링창

1. 관리자(Admin) 점검 항목

🖥️ 관리자(Admin) 전용: 인프라 관제 대시보드

총괄 관리자는 교사들의 참여 현황과 별개로, 시스템의 임계점(Bottleneck)을 실시간으로 추적해야 합니다. 아래 명령어들을 터미널에 띄워두고 모니터링하십시오.

1. CPU & 메모리 부하 
htop
  • • 전체 코어 점유율이 100%를 찍고 내려오지 않는다면, 채점기(judgehost)의 개수를 줄여야 할 신호입니다.
  • • Swap 메모리가 조금이라도 차오르기 시작하면, 즉시 RAM 증설이나 데이터베이스 튜닝을 검토해야 합니다.
  • • Load Average가 코어 수를 초과하는지 체크하십시오.
2. 컨테이너 리소스 상태 
docker stats
  • • domjudge-mariadb 컨테이너의 메모리 사용량을 유심히 보세요. 채점기가 많아질수록 DB가 감당해야 할 IO가 기하급수적으로 늘어납니다.
  • • Judgehost별 CPU 사용률을 개별 확인하여 병목 지점을 탐색하십시오.
3. 로그 및 에러 감지 
docker compose logs -f
  • • 단순히 서버가 죽는 것보다 더 무서운 것은 "채점은 되는데, 제출 결과가 매우 늦게 나오는 상황"입니다.
  • • 로그에서 Connection refused나 Timeout 키워드가 반복적으로 뜨는지 확인하십시오.
4. 네트워크 병목 
nload
  • • 초당 트래픽 급증 구간 확인
  • • 수십 명 동시 접속 시 NIC 대역폭 한계 측정

2. 시나리오별 점검 항목

단계 테스트 유형 방법 목표 및 확인사항
1단계 동시 접속 참가자 전원이 메인 페이지와 스코어보드를 동시에 무한 새로고침(F5) Nginx 응답 지연 발생 여부 확인
2단계 대량 제출 전원이 정답 코드를 10초간 연속으로 제출 Judging Lag 상승 폭 확인 및 채점기 확장 필요성 결정
3단계 무한 루프 while(1); 코드 제출 TLE(시간 초과) 정상 판정 및 시스템 격리 확인
4단계 메모리 폭탄 거대 배열 선언 코드 제출 MLE(메모리 초과) 판정 및 Swap 메모리 작동 확인

3. 단계별 테스트 코드 예시

3단계: TLE 테스트 코드 (C++)

#include <iostream>
int main() {
    // 의도적인 무한 루프 발생
    while(true) {
        // CPU 점유율을 높여 채점기 부하 테스트
    }
    return 0;
}

4단계: MLE 테스트 코드 (C++)

#include <iostream>
#include <vector>

int main() {
    // 약 1GB 이상의 메모리 할당 시도
    std::vector<long long> v(125000000, 1);
    std::cout << v[0] << std::endl;
    return 0;
}
